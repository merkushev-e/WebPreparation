# Interview Prep Tracker

Трекер девятинедельной программы подготовки к собеседованиям на Android/Kotlin —
с 1 августа по 4 октября 2026, 65 дней, 445 вопросов.

Приложение локальное: один HTML-файл, никакого сервера и никакой установки.
Работает без интернета — в самолёте, в метро, где угодно.

---

## Как пользоваться

1. Нажмите зелёную кнопку **Code** вверху страницы репозитория → **Download ZIP**.
2. Распакуйте архив.
3. Откройте файл **`dist/index.html`** двойным кликом.

Всё. Приложение откроется в браузере и будет работать.

> Можно перетащить `dist/index.html` в закладки — открывается как обычная страница.

### Что внутри

| Раздел | Зачем |
|---|---|
| **Сегодня** | текущий день: чекбоксы, оценка уверенности 🔴 / 🟡 / 🟢, режим 20 / 60 / 120 минут |
| **Программа** | все 10 недель и 65 дней с прогрессом, переход в любой день |
| **Красная зона** | две вкладки: 🔴 «Не даётся» и «Отложено»; группировка по темам, фильтры, «Случайные 5» |
| **Поиск** | мгновенный поиск по всем пунктам с подсветкой и переходом на день |
| **Статистика** | прогноз финиша и темп, прогресс по неделям, распределение оценок, серия |
| **Настройки** | норма дня, плавающий календарь, сдвиг стартовой даты, экспорт/импорт, тема, сброс |

Плюс таймер в правом нижнем углу: пресеты 20 / 40 / 45 / 50 / 60 минут и произвольное
значение, звуковой сигнал по окончании, продолжает идти при переключении разделов.

### Режимы дня — кумулятивные

«+40 мин» означает **в дополнение** к первым 20, а не вместо них.

- **20 минут** — только первый блок. Это выполнение плана, а не провал.
- **60 минут** — блоки «20 мин» + «+40 мин».
- **120 минут** — все три блока.

Блоки сверх выбранного режима не прячутся: они приглушены и раскрываются по клику.

### Норма дня, плавающий календарь и «Отложено»

**Норма дня** (по умолчанию 60 минут) — сколько нужно закрыть, чтобы день считался
пройденным. Как только все пункты нормы отмечены, день закрывается сам. Кнопка
«Завершить досрочно» позволяет закрыть день, не выполнив норму.

**Плавающий календарь** (включён по умолчанию): «Сегодня» показывает первый незакрытый
день программы. Пропустили — программа сдвигается, день не сгорает. Плановые даты в
разделе «Программа» при этом не меняются, а на карточке дня видно отставание.

**«Отложено»** — вторая вкладка «Красной зоны». Туда попадают пункты из уже закрытых
дней, которые вы не отметили: весь блок «+60 мин» и всё, что осталось при досрочном
закрытии. Это витрина, а не перемещение — пункт остаётся на своём месте в дне. Отметить
сделанным можно прямо в списке. К неделям 8–9, зарезервированным в программе под
добивание, у вас будет готовый список для прогона.

Арифметика: норма 60 минут — это 371 пункт, **64% программы**, и финиш ровно 4 октября.
Блок «+60 мин» — оставшиеся 206 пунктов, максимум того, что может накопиться в «Отложено».

### Где хранится прогресс

В `localStorage` вашего браузера, ключ `interview-prep-v1`. Ничего никуда не отправляется.

**Важно:** хранилище привязано к адресу. Прогресс, накопленный при открытии файла
локально, **не переедет** сам на `https://…`, и наоборот — для браузера это разные
хранилища. Переносить нужно вручную: **Настройки → Экспорт в JSON**, затем на новом
адресе **Импорт из JSON**. Это же касается смены браузера и режима инкогнито.

### Если начинаете не 1 августа

**Настройки → Дата старта программы.** Все 65 дат пересчитаются, структура недель
сохранится, отметки не потеряются — прогресс привязан к пунктам, а не к датам.
Рядом две кнопки быстрого старта: **«Начать сегодня»** и **«Начать завтра»**.

Плановая дата программы — 1 августа 2026, и к моменту, когда вы открываете приложение,
она обычно уже в прошлом. Поэтому при первом запуске старт ставится на **завтра**, чтобы
не встречать вас отставанием за дни, которых вы не видели. Отставание вообще не
показывается, пока не закрыт хотя бы один день.

## Если захотите открыть доступ через интернет

Тот же файл работает и на статическом хостинге — второй сборки не требуется.
В настройках репозитория откройте **Settings → Pages**, в разделе *Build and deployment*
выберите источник **Deploy from a branch**, ветку с вашим кодом и папку **`/docs`**, затем
**Save**; через минуту приложение будет доступно по адресу вида
`https://<логин>.github.io/<репозиторий>/`.

`docs/index.html` — байт-в-байт копия `dist/index.html`, она создаётся автоматически при
сборке. Отдельная папка нужна потому, что GitHub Pages умеет отдавать только корень
репозитория или `/docs` — выбрать `/dist` в интерфейсе нельзя.

**Учтите:** публичный репозиторий с GitHub Pages виден всем — и сама программа, и
исходники. Ваши отметки о прогрессе при этом остаются в браузере и никуда не
публикуются: в репозиторий попадает только текст программы.

## Для разработки

Node нужен только для пересборки, но не для использования приложения.

```bash
npm run parse    # source/*.md → data/program.json
npm run verify   # сверка эталонных чисел, ненулевой код при расхождении
npm run build    # data + src → dist/index.html (+ docs/index.html)
npm start        # parse + verify + build
```

`npm run build` не соберёт `dist`, если `verify` не прошёл.

### Почему vanilla JS и один файл

Приложение обязано открываться по `file://` двойным кликом. На этом протоколе браузер
блокирует по CORS `fetch()` к локальным файлам и ES-модули (`<script type="module">`),
поэтому сборщики вроде Vite и Webpack не подходят, а данные и код встроены в HTML
инлайном. Никаких CDN, веб-шрифтов и внешних ресурсов — `build.js` проверяет это
автоматически и падает, если что-то из перечисленного просочилось в исходники.

### Что проверяет `verify.js`

Эталонные числа, отсутствие пустых дней, уникальность и формат всех `itemId`,
непрерывность дат с 2026-08-01 по 2026-10-04, дословность текстов (каждый пункт обязан
встречаться в исходном markdown) и сводную таблицу «неделя → дней → пунктов».

```
недель                                  10
дней                                    65
дней с тремя блоками                    64
вопросов (question)                    428
  + шагов каркаса Недели 6              10
  + правил программы                     7
  = пронумерованных строк исходника    445
practice (🛠)                           22   (+1 в правилах программы = 23)
timed (⏱ / **Задача.**)                  7   (+16 дней помечены ⏱ в заголовке)
speak (🎤)                              18
write (✍️)                               3
subtask (- )                            18
```

### Как читаются эталонные числа

В спецификации «445 вопросов» — это все пронумерованные строки исходника. Они
раскладываются так:

- **428** — пункты внутри дней, тип `question`;
- **10** — шаги каркаса ответа Недели 6; по спецификации каркас вынесен в отдельное поле
  недели (`framework`) и показывается памяткой на всех днях Недели 6, поэтому пунктами дня
  он не считается;
- **7** — глобальные правила программы из преамбулы; показаны в разделе «Настройки».

Ни одна строка не потеряна — `verify.js` проверяет, что сумма даёт ровно 445.
Независимая сверка мультимножеств текстов исходника и приложения даёт 445 = 445,
ноль потерянных и ноль лишних.

Кроме вопросов перенесены: заметки недель, риски из сводной таблицы, каркас ответа
Недели 6, глобальные правила, ритм недели и таблица «Проверенный состав» — последние
три показаны в разделе «Настройки». Непереносенной осталась только разметка сводных
таблиц: их шапки и колонка «Тема», дублирующая названия недель другими словами
(«Конкурентность + корутины» против «Конкурентность и фундамент корутин»).

Аналогично с эмодзи-типами: «~23 practice» — это 23 строки с 🛠 в исходнике, из которых
22 находятся внутри дней и стали пунктами, а одна — в глобальных правилах. «~17 timed» —
это 17 вхождений ⏱: 16 в заголовках дней (день помечается флагом «под таймер») и одно в
теле дня; по правилу разбора из спецификации (`⏱` или `**Задача.**`) пунктов типа `timed`
получается 7.

К шести типам из спецификации добавлен седьмой — `task`: прозаические инструкции дня
(«Реализовать через стек изменений», «Подать 3 заявки»). Без него они не имели бы типа
вовсе, а отнести их к `practice` значило бы разойтись с эталонным числом в четыре раза.
