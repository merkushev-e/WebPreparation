# Спецификация: веб-приложение «Interview Prep Tracker»

> Этот файл — задание для Claude Code. Вместе с ним передаётся `android-interview-program-full.md` — это единственный источник данных.

---

## 0. Что нужно сделать

Собрать локальное веб-приложение — трекер прохождения девятинедельной программы подготовки к собеседованиям. Репозиторий на GitHub, пользователь клонирует или скачивает ZIP и **открывает файл в браузере двойным кликом**. Никакого сервера, никакой установки, никакого интернета при использовании.

Приложение показывает программу по дням, даёт отмечать выполненное, ставить каждому вопросу оценку уверенности и собирает «красную зону» из того, что не даётся.

**Интерфейс — на русском. Вопросы внутри — на английском, как в исходнике. Не переводить их.**

---

## 1. Жёсткие ограничения

Это самая важная секция. Нарушение любого пункта делает приложение неработоспособным у пользователя.

1. **Работает по протоколу `file://`.** Пользователь открывает `dist/index.html` двойным кликом. Проверить это руками перед сдачей.
2. **Никаких `fetch()` / `XMLHttpRequest` к локальным файлам.** На `file://` они блокируются CORS. Все данные встроены в HTML как JS-литерал.
3. **Никаких `<script type="module">`.** ES-модули на `file://` тоже блокируются CORS. Только классические скрипты.
4. **Никаких CDN и внешних ресурсов.** Ни шрифтов Google, ни React с unpkg, ни иконочных наборов по сети. Приложение обязано работать в самолёте.
5. **`dist/index.html` — один самодостаточный файл.** CSS инлайном в `<style>`, JS инлайном в `<script>`, данные инлайном, иконки — inline SVG или юникод. Размер до 3 МБ приемлем.
6. **`dist/index.html` закоммичен в репозиторий.** Пользователь не должен запускать npm, чтобы получить рабочее приложение.
7. **Адаптив.** Основной сценарий — десктоп, но с телефона тоже должно открываться и читаться. Минимальная ширина 360px.
8. **Состояние переживает перезагрузку страницы** и не теряется при обновлении `dist/index.html` на новую версию.

## 2. Источник данных

Файл `android-interview-program-full.md`. Написать парсер, который превращает его в `program.json`.

### Правила разбора

| Разметка в markdown | Во что превращается |
|---|---|
| `# НЕДЕЛЯ N · Заголовок (даты)` | объект недели |
| `### Пн 3 авг · Заголовок` | объект дня |
| `**20 мин**` | начало блока tier 1 |
| `**+40 мин**` | начало блока tier 2 |
| `**+60 мин**` | начало блока tier 3 |
| строка вида `12. Текст` | item типа `question` |
| строка с `🛠` | item типа `practice` |
| строка с `⏱` или `**Задача.**` | item типа `timed` |
| строка с `🎤` | item типа `speak` |
| строка с `✍️` | item типа `write` |
| строка `- Текст` | item типа `subtask`, принадлежит предыдущему item |
| `**Design a …**` жирным без маркера | item типа `design` |

### Подводные камни, которые сломают наивный парсер

- **`### Каркас ответа — выучить наизусть…` в Неделе 6 — это НЕ день.** Заголовков `###` в файле 66, дней среди них 65. Отличать по формату: день всегда начинается с сокращения дня недели (`Пн`, `Вт`, `Ср`, `Чт`, `Пт`, `Сб`, `Вс`). Каркас вынести в отдельное поле недели — `framework`, и показывать его как памятку на всех днях Недели 6.
- **Блоки кумулятивные, а не взаимоисключающие.** «+40 мин» означает «в дополнение к первым 20». Режим 60 минут = tier 1 + tier 2. Режим 120 = все три. Не делать из них вкладки-переключатели.
- **Нумерация вопросов не сквозная.** Внутри тем Части 1 она перезапускается, у gotcha-вопросов идёт сквозной ряд 41–110. Поэтому **номер из markdown нельзя использовать как ID.** Генерировать собственные стабильные ID вида `w3-d2-t1-05` (неделя, день, tier, порядковый). ID обязаны быть стабильными между сборками, иначе слетит прогресс.
- **Внутри текстов вопросов есть markdown:** backticks для кода, `**жирный**`, `*курсив*`. Рендерить как `<code>`, `<strong>`, `<em>`. Не выводить сырые звёздочки.
- **Последний день (`Вс 4 окт · Пауза`) не содержит блоков 20/40/60** — только прозаический текст. Парсер не должен на нём падать.
- **Даты в заголовках без года.** Год — 2026. Недели 0–5 это август, дальше сентябрь и октябрь.

### Эталонные числа для самопроверки

После парсинга проверить и вывести в консоль:

```
недель:                 10   (Неделя 0 … Неделя 9)
дней:                   65   (2 в Неделе 0 + 63 в Неделях 1–9)
дней с тремя блоками:   64   (все кроме «Вс 4 окт · Пауза»)
вопросов (question):    445
practice (🛠):          ~23
timed (⏱):             ~17
speak (🎤):             ~18
write (✍️):             3
subtask (- ):           18
```

**Если числа не сходятся — парсер неправильный, чинить парсер, а не подгонять цифры.**

Дополнительно: ни один день не должен получиться пустым. Восемь дней содержат задачи только жирным текстом без нумерации (`Пн 7 сен`, `Вт 8 сен`, `Ср 9 сен`, `Чт 10 сен`, `Чт 24 сен`, `Пт 2 окт`, `Сб 3 окт`, `Вс 4 окт`) — на них парсер обычно и ломается. Проверить их отдельно.

## 3. Модель данных

```ts
type Program = {
  weeks: Week[]
}

type Week = {
  id: string           // "w0" … "w9"
  number: number
  title: string        // "Конкурентность и фундамент корутин"
  dateRange: string    // "3–9 августа"
  risk?: string        // из итоговой таблицы: "Провал live coding в Revolut"
  framework?: string[] // только для Недели 6 — 10 шагов каркаса
  days: Day[]
}

type Day = {
  id: string           // "w1-d1"
  date: string         // "2026-08-03"
  weekday: string      // "Пн"
  title: string        // "Гонки и блокировки"
  hot: boolean         // был ли 🔥 в заголовке
  tiers: Tier[]        // 0 или 3 элемента
  prose?: string       // для дней без блоков
}

type Tier = {
  level: 20 | 40 | 60  // "20 мин", "+40 мин", "+60 мин"
  items: Item[]
}

type Item = {
  id: string           // "w1-d1-t1-01" — СТАБИЛЬНЫЙ
  type: 'question' | 'practice' | 'timed' | 'speak' | 'write' | 'design' | 'subtask'
  text: string         // с сохранённой markdown-разметкой
  note?: string        // текст в скобках-курсиве, если есть
  children?: Item[]    // для subtask
}
```

## 4. Экраны

Шесть разделов, переключение через боковую панель на десктопе и нижнюю навигацию на телефоне.

### 4.1 Сегодня — главный экран

- Карточка текущего дня: неделя, дата, заголовок, метка 🔥 если день критический.
- **Переключатель режима: 20 / 60 / 120 минут.** Выбор влияет на то, какие блоки раскрыты. При 20 показывается только первый блок, остальные свёрнуты и приглушены, но доступны по клику.
- Список пунктов. Каждый пункт — строка с:
  - чекбоксом «сделано»;
  - тремя кнопками уверенности 🔴 / 🟡 / 🟢 (только для типа `question`);
  - иконкой типа слева (🛠 ⏱ 🎤 ✍️);
  - для типа `timed` — кнопкой запуска таймера прямо на строке.
- Полоса прогресса дня: сколько пунктов текущего режима отмечено.
- Кнопка «Завершить день» — фиксирует `completedAt`, показывает короткую сводку: сколько 🟢, сколько 🔴 ушло в красную зону.
- Если сегодня выходит за пределы программы — показать ближайший незавершённый день и подсказку.
- Стрелки «предыдущий / следующий день» без ухода в раздел «Программа».

### 4.2 Программа

- Все 10 недель списком, свёрнуты.
- У недели: номер, тема, диапазон дат, кольцевой прогресс, строка риска из итоговой таблицы.
- Разворот недели — семь дней с их прогрессом. Клик по дню открывает его в режиме экрана «Сегодня».
- Текущая неделя развёрнута по умолчанию и подсвечена.

### 4.3 Красная зона

Главная рабочая ценность приложения.

- Все пункты со статусом 🔴, сгруппированные **по темам**, а не по датам. Тему выводить из недели и заголовка дня (например «Корутины», «Compose», «Архитектура»).
- У каждого пункта — ссылка на день-источник.
- Возможность переставить статус прямо здесь, не уходя на день.
- Счётчик сверху: «17 вопросов в красной зоне».
- Фильтр по темам и переключатель «показывать также 🟡».
- Кнопка «Случайные 5» — вытаскивает пять случайных красных для быстрого прогона.

### 4.4 Поиск

- Одно поле, мгновенный поиск по всем 445+ пунктам без кнопки.
- Совпадения подсвечиваются в тексте.
- В результате: текст пункта, его тип, неделя и день, текущий статус.
- Клик — переход на день с прокруткой к пункту и кратковременной подсветкой.

### 4.5 Статистика

- Прогресс по каждой из 10 недель, столбиками.
- Распределение 🔴 / 🟡 / 🟢 / без оценки — кольцевая диаграмма.
- Серия: сколько дней подряд отмечено хотя бы выполнение режима «20».
- Счётчик: сколько дней осталось до 5 октября.
- Разбивка по типам: сколько пройдено вопросов, задач на код, дизайн-задач, историй.

### 4.6 Настройки

- **Сдвиг стартовой даты.** Если пользователь начинает не 1 августа — пересчитать все даты, сохранив структуру недель. Это обязательная функция, не опциональная.
- Экспорт прогресса в JSON-файл (через `Blob` + `<a download>`, работает на `file://`).
- Импорт JSON.
- Полный сброс с подтверждением.
- Переключатель темы.

## 5. Таймер

- Плавающая кнопка в углу, доступна с любого экрана.
- Пресеты: 20, 40, 45, 50, 60 минут. Плюс произвольное значение.
- При запуске с пункта типа `timed` — подставляет длительность из текста задачи, если она там указана («Таймер 45 минут»).
- Продолжает идти при переключении разделов.
- По завершении: звуковой сигнал через Web Audio API (без внешних файлов) и смена заголовка вкладки.
- Пауза и сброс.

## 6. Хранение состояния

- `localStorage`, один ключ `interview-prep-v1`.
- Запись с дебаунсом 300 мс, чтобы не дёргать на каждый клик.
- **Миграция обязательна:** при чтении проверять `version`, при несовпадении — мягко мигрировать, не стирать. Неизвестные `itemId` игнорировать, а не падать.
- При первом запуске — пустое состояние, без демо-данных.

## 7. Визуальный стиль

- **Тёмная тема по умолчанию.** Спокойная, для работы по часу в день на протяжении двух месяцев.
- Плотная типографика, читаемость важнее воздуха. Это рабочий инструмент, а не лендинг.
- Системный шрифтовой стек, без веб-шрифтов: `-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, sans-serif`. Для кода — `ui-monospace, SFMono-Regular, Menlo, monospace`.
- Цвета статусов: 🔴 приглушённый красный, 🟡 янтарный, 🟢 приглушённый зелёный. Не кислотные.
- **Никакой геймификации.** Никаких конфетти, бейджей, «ачивок», мотивационных цитат. Прогресс-бар и цифры — достаточно.
- Анимации минимальные: раскрытие блока, подсветка найденного. Не больше 150 мс.
- Уважать `prefers-reduced-motion`.

## 8. Технологии

- **Vanilla JS.** Никаких фреймворков — они тянут либо CDN, либо сборку в модули, а это нарушает ограничения из секции 1. Приложение простое, состояние небольшое, рендер по перерисовке секции достаточен.
- CSS — обычный, с кастомными свойствами для темы. Без препроцессоров.
- Node нужен только для сборки и проверки, не для запуска.

- `npm run parse` — перегенерировать `data/program.json` из markdown

- `npm start` — parse + verify + build

`README.md` пишется для человека, который просто хочет пользоваться: скачать ZIP, распаковать, открыть `dist/index.html`. Инструкции для разработки — ниже, отдельным разделом.

## 10. Обязательный шаг проверки полноты

`scripts/verify.js` должен:

1. Сверить все числа из раздела «Эталонные числа» и упасть при расхождении, показав, что именно не сошлось.
2. Проверить, что ни один из 65 дней не пустой.
3. Проверить уникальность всех `itemId`.
4. Проверить, что даты идут непрерывно с 2026-08-01 по 2026-10-04 без дыр и дублей.
5. Вывести таблицу: неделя → число дней → число пунктов.

`npm run build` не должен собирать `dist`, если `verify` не прошёл.

## 11. Критерии приёмки

Проверяется вручную перед сдачей. Каждый пункт — да или нет.

1. `dist/index.html` открывается двойным кликом из файлового менеджера, приложение полностью работает.
2. В консоли браузера нет ошибок.
3. Отключён интернет — приложение работает без изменений.
4. Все 65 дней открываются, ни один не пустой.
5. Все 445 вопросов присутствуют, текст совпадает с исходником дословно, включая форматирование кода.
6. Переключение 20 / 60 / 120 меняет объём дня кумулятивно.
7. Отметки и оценки переживают перезагрузку страницы.
8. Пункт, помеченный 🔴, немедленно появляется в разделе «Красная зона».
9. Поиск находит вопрос по фрагменту текста и переводит на нужный день.
10. Сдвиг стартовой даты пересчитывает все 65 дат, прогресс не теряется.
11. Экспорт даёт валидный JSON, импорт его принимает и восстанавливает состояние.
12. Таймер работает при переключении разделов.
13. Открывается на телефоне шириной 360px без горизонтальной прокрутки.
14. `npm run verify` проходит.

## 11.5 Хостинг

Пользователь может позже выложить приложение в сеть. Специально ничего для этого делать не нужно: тот же `dist/index.html` работает и локально по `file://`, и на любом статическом хостинге по `https://`. Это одно из главных преимуществ выбранного подхода — второй сборки не требуется.

**Что нужно предусмотреть:**

1. **Все пути внутри файла — относительные или отсутствуют.** Никаких `/assets/...` от корня: на `file://` они сломаются.
2. **Предупреждение о переносе прогресса.** `localStorage` привязан к origin. Прогресс, накопленный при открытии файла локально, **не переедет** на `https://адрес-сайта` автоматически — для браузера это разные хранилища. То же самое при смене домена.
   Поэтому в разделе «Настройки» рядом с кнопкой экспорта разместить короткую поясняющую строку: *«Прогресс хранится отдельно для каждого адреса. Если откроете приложение по другому адресу — перенесите прогресс через экспорт и импорт»*. Это единственный способ, и пользователь должен узнать о нём до того, как потеряет месяц отметок.
3. **В README — раздел «Если захотите открыть доступ через интернет»** с самым коротким рабочим путём: включить GitHub Pages в настройках репозитория, указать папку `/dist`. Одним абзацем, без вариантов на выбор.
4. **Упомянуть в README, что публичный репозиторий с GitHub Pages виден всем.** Сами отметки о прогрессе при этом остаются в браузере и никуда не публикуются — в репозиторий попадает только программа.

## 12. Чего делать не нужно

- Бэкенда, базы данных, аккаунтов, синхронизации между устройствами.
- Сборщиков вроде Vite или Webpack — они дают ES-модули, несовместимые с `file://`.
- React, Vue, Svelte, Tailwind по CDN.
- Service Worker и PWA-манифеста — приложение и так локальное.
- Правки текстов вопросов: сокращений, переводов, перефразировок. Программа переносится дословно.
- Собственных «улучшений» программы: добавления вопросов, перестановки дней, изменения формулировок.
- Анализа, «сколько вам ещё учить» и мотивационных подсказок.

## 13. Порядок работы

1. Прочитать `android-interview-program-full.md` целиком, прежде чем писать парсер.
2. Написать `parse.js`, прогнать, сверить с эталонными числами. **Не двигаться дальше, пока не сойдётся.**
3. Написать `verify.js`.
4. Сделать вёрстку и логику одного экрана «Сегодня» полностью, проверить на `file://`.
